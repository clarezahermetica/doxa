## Principle

Multi-agent behavior is a first-class DOXA configuration, not an ornamental chat room. Agents exchange structured artifacts and arguments that become part of the same versioned experimental history.

## Roles

<b>Executor</b> advances the task and takes allowed actions.

<b>Skeptic</b> attacks assumptions, searches for failure modes, and issues structured challenges.

<b>Researcher</b> retrieves or gathers evidence when the task supports it.

<b>Archivist</b> proposes memory classifications and provenance-preserving summaries.

<b>Orchestrator</b> is primarily deterministic software controlling sequence, permissions, budgets, and state.

<b>Verifier</b> is an independent evaluation layer using executable checks, answer keys, task constraints, or clearly typed evaluative models.

One model may fill several roles in separate calls; different model families may occupy different roles. The experiment record must preserve the assignment.

## Operating modes

### Solo

One main agent works with DOXA's external tool, verification, memory, and recovery machinery.

### Collaborative

Multiple agents pursue a shared goal. They can divide subtasks, independently investigate, share evidence, and merge artifacts. Private reflections remain distinct from the shared evidence ledger.

### Adversarial

An Executor advances a solution while one or more Skeptics challenge decisions. Criticism is evaluated, not presumed valid.

## Typed council messages

Recommended message types: CLAIM, EVIDENCE, CHALLENGE, RESPONSE, ACTION, VERIFICATION, MEMORY\_PROPOSAL, REQUEST\_EVIDENCE, HANDOFF, and RESOLUTION.

Every message should reference experiment, trajectory or branch, sender, target where relevant, and linked claim or evidence IDs.

## Council research questions

- Does collaboration outperform a solo agent at matched or reported compute?
- Does cross-model criticism reveal errors missed by same-model critique?
- When does shared memory spread a mistake?
- Does independent parallel work outperform interactive debate?
- Can a council converge confidently on a false assumption?

## Acceptance tests

1. Complete a solo run.
2. Complete a collaborative run with at least two identifiable agent contributions.
3. Complete an adversarial run with a challenge linked to a target decision.
4. Preserve private and shared records separately.
5. Record model and role assignments and costs.
6. Display disagreement without overwriting minority positions.

## Locked Solo Deliberative protocol — October 12, 2026

- Solo mode has two named configurations: <b>Solo Direct</b> (one task-oriented agent with external verifier) and <b>Solo Deliberative</b> (the same physical model in sequential Proposer, Skeptic, Defender, and Adjudicator calls).
- Separate role contexts so critiques are not silently contaminated by persuasive prior justifications; critics and adjudicators are not independent ground truth.
- Workflow: record claim/action → generate targeted criticism → check against external evidence → defend/revise/qualify/abstain → apply deterministic policy → govern candidate lesson in memory. Limit critique rounds (default no more than 2 without new verifiable evidence).
- Outcomes include Retain, Qualify, Revise, Investigate and Abstain; accepting an unsupported objection is a measurable failure, as is refusing a supported correction.
- Cross-family Council is optional; one provider/model can occupy several roles. Preserve role context, disclosure, and provider assignment in Experiment Ledger. Budget matching required when comparing policies.
- CLI and local Studio expose the same role/claims/challenge/verification records without requiring a public network server.
