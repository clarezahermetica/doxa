## Recommended default stack

### Core runtime

<b>Python</b> for orchestration, research logic, environment adapters, evaluation, and model/provider interfaces.

<b>FastAPI</b> for the local HTTP API between runtime and Studio.

<b>Pydantic or equivalent typed models</b> for shared event/entity schemas and validation.

<b>SQLite</b> for local persistence, with migrations from the beginning.

<b>Typer</b> or a comparable Python CLI framework for terminal commands.

### Studio

<b>TypeScript + React</b> with a lightweight local frontend build. React Flow or a similar graph component is a candidate for branch/decision visualization. The choice between Vite and Next.js should be driven by local-app simplicity rather than public-site deployment needs.

### Execution

Disposable Git worktrees or isolated task directories for code-repair state, plus a stronger process/container sandbox for generated code execution.

### Remote inference

Provider adapters for hosted APIs and a RunPod-backed self-hosted endpoint. If an open-weight model is served remotely, vLLM is a candidate because of its model-serving focus and familiar HTTP patterns.

## Repository topology

Recommended top-level modules:

- core — orchestration, IDs, policies, shared types.
- systems — the six named DOXA capabilities.
- providers — model adapters and capability declarations.
- environments — code repair, research, planning.
- storage — database and artifact persistence.
- evaluation — task verifiers, metrics, run comparisons.
- annotation — rubrics, preferences, exports.
- api — local FastAPI surface.
- cli — terminal commands.
- studio — TypeScript/React interface.
- tests — unit, contract, and end-to-end tests.
- examples — reproducible experiments and recorded trajectories.
- docs — architecture, research lineage, installation, limitations.

## Testing hierarchy

<b>Unit tests</b> for state transitions and serializers.

<b>Contract tests</b> for providers and environments.

<b>Integration tests</b> for system interactions such as challenge → verification → rollback.

<b>End-to-end tests</b> for one complete experiment in each operating mode.

<b>Golden/fixture tests</b> for recorded trajectories and deterministic UI/API reconstruction.

## Codex discipline

Codex tasks should target narrow contracts. Avoid concurrent rewrites of the same shared schema. Require tests for every core module before integration. Preserve a known-good main branch once the first end-to-end flow works.

## Stack now locked — October 12, 2026

- Runtime: Python 3.12+, FastAPI, Pydantic, deterministic controller/state machine.
- Persistence: local SQLite, Alembic migrations, filesystem/content-hash artifact manifests; shared append-only Experiment Ledger is the central deliverable.
- CLI: Typer. Studio: React + TypeScript + Vite, React Flow for branch visualization. No Next.js or public hosted website in v1.
- Local execution: disposable Git worktrees/task directories plus separately restricted container execution for model-generated code; default deny network, read-only base filesystem where feasible, CPU/memory/time quotas, no provider secrets in the sandbox.
- Provider interface: separate OpenAI and Google Gemini hosted API adapters plus an optional OpenAI-compatible adapter for self-hosted inference. Remote RunPod/vLLM is optional rather than an architectural dependency. Start with sequential model calls, bounded retries, strict structured-response validation.
- Interfaces share the same local FastAPI backend bound to 127.0.0.1 and local persistence. Background job queue and Tauri desktop packaging are deferred unless requirements demonstrate necessity; do not introduce a public service.
- <b>Operating cost cap:</b> \$75 total for DOXA experimentation/inference/optional GPU during the hackathon; controller tracks estimates per provider and stops or requests explicit budget approval at its configured cap. Provider dashboard billing limits are independently recommended.
- Test priority: ledger integrity and actual environment checkpoint restore before visual polish. Exact model IDs and prices are runtime configuration, not hard-coded assumptions.
