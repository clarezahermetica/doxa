## Purpose

Memory Tribunal governs what information from completed or failed trajectories can influence later behavior. Its central premise is that an agent-generated reflection is evidence about what the agent said it learned, not automatic evidence that the lesson is true.

## Memory categories

<b>Episodic</b> — records of particular attempts or experiences.

<b>Semantic</b> — propositions about tools, environments, tasks, or domains.

<b>Procedural</b> — reusable strategies or instructions.

<b>Reflective</b> — interpretations of why an attempt succeeded or failed.

<b>Shared</b> — evidence-linked records explicitly made available to multiple agents.

## Trust states

<b>Verified</b> — supported by the configured verification procedure within a defined scope.

<b>Quarantined</b> — retained as potentially useful but excluded from trusted retrieval or clearly marked as provisional.

<b>Rejected</b> — preserved for audit but excluded from guidance.

A memory can later be promoted, demoted, scoped more narrowly, or revoked.

## Provenance

Every memory must link to its originating trajectory, event or decision, author, evidence, creation method, current trust state, and revision history. Memories from abandoned branches must retain that branch provenance.

## Agent-specific vs shared memory

Each agent can maintain a private history. Shared records should be explicitly promoted into a group evidence ledger rather than silently copied from one agent's internal notes. This enables experiments on whether sharing reflections improves cooperation or spreads errors.

## Retrieval policy

Trusted retrieval should prefer verified memories whose scope matches the current task. Quarantined memories may be shown as hypotheses but must remain visibly provisional. Rejected memories can appear in audit views but should not act as default guidance.

## Acceptance tests

1. Propose a memory from a failed trajectory.
2. Quarantine it and verify it is excluded from trusted retrieval.
3. Promote a verified narrower lesson and retrieve it on a later task.
4. Revoke a previously verified memory and verify future retrieval respects the change.
5. Preserve provenance to an abandoned branch.
6. Keep separate agent-private memories while maintaining an explicitly shared evidence store.

## Integrated ledger acceptance addendum — October 12, 2026

- Memory is an integrated, governed experiment resource; the historical “Memory Tribunal” label need not appear as a prominent brand.
- Every memory proposal, quarantine, promotion, revocation and retrieval is linked to source trajectory, evidence and trust scope in the shared ledger. Promoted evidence from an abandoned branch retains that origin.
- Quarantined or rejected lessons never enter default trusted retrieval. Explicit council sharing only; no accidental promotion of role-private notes.
- Acceptance: quarantine an overly broad cache-failure lesson, promote a narrower independently supported observation, then verify post-restart retrieval and revocation semantics through CLI/Studio.

## Moss retrieval prototype addendum — October 24, 2026

<b>Scope.</b> Evaluate Moss as an optional fast search backend beneath Memory Tribunal; this does not change Tribunal's responsibility to admit, reject, scope and revoke memories. The canonical SQLite record and append-only ledger govern truth, eligibility and provenance. A Moss index is only a rebuildable retrieval view.

<b>Adapter contract.</b> Search input includes requesting agent, task/run/branch, eligible scopes, query and requested count. Results contain stable memory IDs, scores, originating episode/branch and backend/index version when available. The controller cross-checks each candidate's current verified status, scope/ownership, revocation, supersession and validation references against SQLite <b>after retrieval and before prompt injection</b>, so delayed index refresh cannot leak revoked or private memories. Quarantined/rejected memories remain available in audit views but not trusted context.

<b>Synthetic acceptance fixture.</b> Agent A and B each have private lessons; one memory is deliberately shared after promotion; one tempting false lesson remains quarantined; one verified lesson is revoked; a superseded lesson has a corrected successor. Confirm A/B isolation, explicitly shared retrieval, accepted retrieval, zero normal-context contamination, post-restart repeatability and operation without Moss. Repeat with a deliberately stale index and compare with a SQLite-only baseline. Record actual timing, correctness and any credit usage, not promised performance.

<b>Open technical questions.</b> Select separate indexes versus metadata filtering based on tested isolation/limits; determine local session persistence and cross-process update semantics; verify the reported \$100 credit's scope and expiry. Do not promote Moss from optional to required without passing these checks.
