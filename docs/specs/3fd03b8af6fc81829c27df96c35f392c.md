## 1. Thesis and scope

<b>DOXA is a local-first experimental framework for studying and improving an AI agent's epistemic trajectory</b>: the sequence of commitments it makes, the evidence for them, challenges and tests encountered, revisions adopted or rejected, and memories retained. The central artifact is an <b>append-only experiment ledger</b>, not merely a debate transcript or free-form reflection log.

<b>Research question:</b> Under what conditions do versioned commitments, independently tested criticism, counterfactual branching, controlled memory, and bounded reflection improve real task outcomes enough to justify their added cost?

The hackathon deliverable is an integrated first implementation of <b>Epistemic Git, Counterfactual Engine, False Critic, Memory Tribunal, Self-Correction Gym, and Adaptive Reflection</b>. The project should remain a coherent whole, not six disconnected buttons or a reduced "Lite" rebranding.

<b>Out of scope for this release:</b> training a new foundation model, DPO/RL/RLHF, autonomous production deployment, open-ended browsing, a public SaaS, inferring private model chain-of-thought, or interpreting one successful demo as proof of improved reasoning. Large-scale replication, more task environments, learned intervention policies, and broader model families are post-hackathon work.

## 3. Architecture and source of truth

### Core stack

- <b>Controller/backend:</b> Python, FastAPI, Pydantic. A deterministic controller owns state transitions and emits events. Model text supplies proposals and evidence candidates; it cannot silently authorize mutations.
- <b>Persistence:</b> SQLite for event ledger and indexed records, with a local artifact store for patches, checkpoints, test logs, prompts/config snapshots and exports. Content-hash consequential artifacts.
- <b>CLI:</b> Typer; the same controller and persistence used by the visual interface.
- <b>Studio:</b> React, TypeScript, Vite, React Flow; [localhost](http://localhost), no public deployment required.
- <b>Providers:</b> typed model adapters recording provider, model ID, sampling/configuration, response status, error information, token usage and costs where observable. Compare protocols with the same base model where feasible.
- <b>Optional compute:</b> remote GPU/RunPod or hosted inference may be configured, but not required for local orchestration. Mock inference is a unit-testing mechanism, <b>not</b> empirical evidence.
- <b>Execution:</b> generated or modified code runs inside disposable restricted containers, without network by default; time, filesystem, CPU and memory limits must be enforced. If adequate isolation is unavailable, <b>disable execution</b> rather than execute untrusted patches against the host.
- <b>Spend:</b> \$75 hard total ceiling covering API and remote compute; configurable per-run soft and hard ceilings; the system must reject a cost-incurring action if it would violate enforced limits. Record unknown actual billing as unknown, not zero.

### Append-only experiment ledger

Each experiment has a stable run ID. Each branch has a branch ID, parent branch ID, and origin checkpoint ID. Each event records a unique event ID, run ID, branch, per-branch logical sequence, UTC time, typed event name, actor/agent, provenance type, payload version, causal parent event IDs, model configuration reference where applicable, artifact refs and hashes, and an idempotency/deduplication key for consequential actions.

<b>The ledger is immutable even when working state is restored.</b> A checkpoint captures task version, fixture, source/workspace artifact hash, environment image/config, observations/test results, memory snapshot, model config, and event cursor. Restoration checks relevant hashes, creates new branch ancestry, and never erases the parent.

The existing Event Model page includes a more expansive uppercase event vocabulary. <b>Normalization decision:</b> use a single canonical, typed event enum for implementation, with a documented mapping from legacy draft names, rather than emitting two mixed naming schemes. Core semantic events must cover task and environment initialization, observations, claims, evidence, decisions, tools/tests, criticisms and adjudication, checkpoints and restore, forks, revisions, memory lifecycle, reflection trigger/skip, evaluations, human annotations and run close.

<b>Provenance is not interchangeable:</b> model assertion, tool observation, deterministic verification, task answer key, LLM evaluation, human annotation and imported source remain distinct. Model consensus alone is not verification. Never export API secrets.

### Claim, checkpoint and memory contracts

A claim is a short inspectable proposition/decision with status (proposed, contested, supported, rejected, superseded), evidence references and dependencies. It is not a reconstruction of the model's private thoughts.

A checkpoint pins reproducible <i>observable</i> state. A replay of stored model output must say REPLAY; fresh stochastic inference is a new sample, not a deterministic replay. Restore evidence should include artifact hash comparison.

A memory record carries provenance, scope (agent-private or shared), trust state, source episode, validation references, eligibility conditions and revocation status. An unverified or revoked memory must not be silently retrieved as approved knowledge.

## 4. Six core capabilities — implementation contracts

### A. Epistemic Git

<b>Input:</b> assertions, evidence, decisions, revisions, and adjudications.

<b>Mechanism:</b> append immutable claim/evidence/revision events; maintain dependency references and statuses; produce a diff of commitments and supporting evidence between checkpoints.

<b>Output:</b> a history answering what changed, when, because of which evidence, under whose authorization.

<b>Acceptance:</b> a proposed claim becomes supported and later superseded; the old state and evidence remain inspectable after a fork.

### B. Counterfactual Engine

<b>Input:</b> checkpoint, explicit intervention, remaining budget.

<b>Mechanism:</b> restore the pinned task, artifacts, environment and eligible memory into an isolated alternative branch; apply a declared change and continue without mutating parent history.

<b>Output:</b> side-by-side patch/state diffs, task scores, resource differences and intervention summary.

<b>Acceptance:</b> fork directly before criticism: branch A accepts an objection and branch B rejects it, both preserve the parent and report relevant stochastic confounders. Branch comparison is not automatic proof of a causal effect.

### C. False Critic

<b>Input:</b> objection linked to a specific claim, proposed defect, proposed revision and reproducible test/evidence (or a declared unverified rationale).

<b>Mechanism:</b> independently adjudicate via test, deterministic check, or credible external task oracle. Verdict is valid, invalid or unverified. Another LLM's agreement is not ground truth.

<b>Output:</b> objection, evidence, verdict, and permitted/rejected/deferred revision.

<b>Acceptance:</b> a true criticism leads to an evidence-backed correction; a convincing false criticism does not damage an already passing artifact; rejected objections remain visible.

### D. Memory Tribunal

<b>Input:</b> candidate reusable lesson from observed trajectory.

<b>Mechanism:</b> quarantine by default; promote only with provenance and a completed validation gate; support later contradiction and revocation. Scope memory to agent/private versus explicitly shared.

<b>Output:</b> eligibility-filtered retrieval set with origin, trust state and validation metadata.

<b>Acceptance:</b> a plausible false lesson stays quarantined and cannot contaminate the next attempt; a verified lesson can be promoted and retrieved; a revoked lesson is excluded from future normal retrieval.

### E. Self-Correction Gym

<b>Input:</b> versioned task fixture, tests/oracles, baseline, treatment policy, evaluator version, optional human rubric.

<b>Mechanism:</b> run matched attempts, retain failed and successful trajectories, compare intervention outcomes, produce reproducible metrics and export structured records. Human trajectory-quality ratings and pairwise preferences remain separate from automated correctness.

<b>Output:</b> per-run correctness, recovery/regression, latency, tokens, dollars, event lineage, human labels, and cross-mode comparisons.

<b>Acceptance:</b> baseline and treatment execute against the same task version; Studio and export show failure cases as well as successes, with attributable model IDs and resource cost.

### F. Adaptive Reflection

<b>Input:</b> test failure, new validated criticism, contradiction, stagnation, successful validation, and budget remaining.

<b>Mechanism:</b> an explicit rule-based v0.1 controller chooses continue, verify/test, retrieve, critique/reflect, fork/rollback, escalate, or stop. Every trigger and decision is recorded. Use an initial limit of <b>at most two reflection interventions per branch</b>, bounded further by cost and time.

<b>Output:</b> transparent reason-coded decisions, including justified <i>skips</i>.

<b>Acceptance:</b> a failing test can trigger targeted reflection; an invalid criticism need not; passing solution with no new evidence stops; budget exhaustion prevents further model spending.

## 5. Agent protocols

All modes share the same fixture format, event schema, evaluator, persistence and controller.

- <b>Solo Direct:</b> a single proposer attempt followed by ordinary task verification. It is the essential baseline, without an additional critique stage.
- <b>Solo Deliberative:</b> one model sequentially occupies proposer, critic and reviser roles while external tests adjudicate correctness.
- <b>Collaborative Multi-agent:</b> distinct proposer and verifier/repairer roles share scoped observations and attempt cooperative correction.
- <b>Adversarial Multi-agent:</b> proposer faces a challenger, but criticism must pass an evidence gate before changing the canonical result.

The existing <b>Agent Council</b> specifications remain companion contracts for agent identity, role permissions, dialogue and information sharing. Calling the same model with different roles is not independent evidence. Record model IDs, prompts, call counts, permission differences, runtime and cost.

## 6. Flagship end-to-end demonstration

<b>Fixture:</b> a stateful cache-invalidation code-repair exercise. A cache returns stale data when an underlying object is modified or removed. Deterministic tests check reads, update/remove invalidation, and regression behavior. Establish a known faulty starting artifact and a candidate patch with visible test consequences.

1. <b>Propose:</b> agent records short diagnosis and patch; ledger captures claim, patch hash, and initial tests.
2. <b>Observe:</b> a failing hidden/regression test reports a stale-cache failure with reproducible evidence.
3. <b>Critique:</b> inject a true objection and a plausible but false objection, each tied to a proposed change.
4. <b>Adjudicate:</b> independently test; invalid criticism is rejected or deferred rather than silently obeyed.
5. <b>Fork:</b> restore a common checkpoint and compare accept-versus-reject criticism interventions; parent remains immutable.
6. <b>Tribunal:</b> quarantine a misleading generalized lesson; promote a narrower lesson supported by passing validation, then show filtered retrieval on a related task.
7. <b>Reflect:</b> explain why further checking was justified after failure, and why unnecessary reflection was skipped after success or invalid criticism.
8. <b>Evaluate:</b> compare Solo Direct, Solo Deliberative and at least one multi-agent mode in Studio; show actual task checks, regressions, branch diffs, cost and trajectory.
9. <b>Annotate:</b> record a human trajectory-quality label or preference separately from objective test outcomes; export it alongside but not conflated with model or verifier provenance.

<b>Negative-control fixtures:</b> (a) misleading criticism of already correct code; (b) poisoned or stale lesson with memory quarantine/revocation. They test integration and failure handling, not statistical generalization.

<b>Research showcase stretch:</b> companion demo plan suggests one feasible SciCode task (candidate Haldane-model/Chern-number phase diagram or N-body subproblem), with exact official evaluator feasibility checked first; a DS-1000 correct-code/false-critique negative control is another candidate. SWE-bench is optional only if its environment is feasible. These do not replace the cache invalidation flagship.

Deterministic tests—not an LLM judge alone—decide code correctness. A recorded fallback demonstration may be used but should visibly display <b>REPLAY</b> and retain raw historical artifacts.

## 7. Evaluation and falsifiable metrics

- <b>Task success:</b> held-out checks passed; full oracle success.
- <b>Recovery:</b> initially failing attempts that become passing, with denominator.
- <b>False-correction/regression:</b> previously passing attempts damaged by unsupported interventions, with denominator.
- <b>Critic discrimination:</b> true/false labeled criticisms handled correctly; unverified judgments remain separate.
- <b>Repeat-error:</b> validated failures recurring in later retries or related fixtures.
- <b>Memory contamination:</b> false lessons promoted/retrieved or resulting in traceable downstream errors.
- <b>Efficiency:</b> provider calls, input/output tokens when known, test executions, wall time, cost per successful repair.
- <b>Trace integrity:</b> proportion of accepted revisions linked to evidence or test observations.
- <b>Human feedback:</b> trajectory quality, process labels, desirability, pairwise preferences and reviewer provenance, reported distinctly from oracle score.

<b>Protocol hygiene:</b> establish acceptance checks before testing; run at least Solo Direct against the same fixtures; preserve all failures; note differences in model, seed, tokens, prompt, time and environmental randomness; don't claim exact causal isolation unless intervention is genuinely controlled; don't infer superiority from a handful of demos. This is exploratory engineering/research until repeated and independently checked.

## 8. Studio and CLI

<b>Studio information hierarchy:</b>

1. Run overview — task, status, mode, model(s), resource budget and current decision.
2. Trajectory — decisions, observations, tests, objections, verifications, revisions and intervention reasons.
3. Branch graph and diff — clickable checkpoints, parent/child lineage, source/state diffs, outcome and cost comparisons.
4. Claims, evidence and memory — claim statuses, provenance, quarantines, promotions and revocations.
5. Gym and Annotation Studio — matched baselines, negative controls, automated metrics and human quality/preference labels.

<b>CLI (proposed command grammar; not yet implemented):</b> run a fixture with a selected mode; inspect one run; fork at checkpoint with explicit intervention; compare runs; evaluate a suite; export JSON. Keep CLI and Studio thin—both query the same authoritative backend.

<b>HTTP surface (proposed):</b> create/get runs; list run events; fork at checkpoint; list claims/memory; execute/list evaluations; export structured bundle. Studio subscribes or polls persisted events and never invents shadow experiment state.

## 9. Release gates — no feature theater

- [ ] All six capabilities perform a real, observable action, not placeholders.
- [ ] Four named protocols execute through one controller; no disguised alias.
- [ ] An actual checkpoint restores correctly and forks without mutating the parent.
- [ ] Valid and false objections receive different evidence-backed adjudication.
- [ ] Memory quarantine/promotion/revocation and retrieval filtering work.
- [ ] Reflection trigger, skip and hard stops are observable and bounded.
- [ ] At least one deterministic fixture reports successful <b>and unsuccessful</b> runs, with real test outputs.
- [ ] CLI and Studio display the same persisted run; exports include provenance, model and fixture versions.
- [ ] At least one actual model backend works; mocked/replayed output is labeled.
- [ ] Human labeling and preference metadata are saved as a distinct provenance type.
- [ ] Sandbox execution and global/per-run spending ceilings are enforced.
- [ ] README documents installation, architecture, demo sequence, evidence limits, costs and honest project status.
- [ ] Submission image, repository, table number, recorded demo and presentation are prepared and deadline checked.

<b>If time is short:</b> reduce aesthetic polish, number of benchmark fixtures and optional visualizations first. Preserve the ledger, evidence gate, actual restore, memory status gate, common evaluation model and complete six-system execution path.

## 10. Dependency-aware implementation order

1. Fixtures and schemas; event/claim/evidence/artifact IDs; atomic append-only SQLite persistence; cost accounting and export.
2. One typed real provider adapter and restricted code test runner; Solo Direct executes end to end.
3. Checkpoint/hash manifest, restore, ancestry, claim diffs; integrate Epistemic Git and Counterfactual Engine.
4. Challenge objects, deterministic verification, verdict and permitted/rejected revision path; integrate False Critic.
5. Quarantine/promotion/revocation state machine, scope-aware retrieval; integrate Memory Tribunal.
6. Rule-based adaptive reflection with triggers, skip reasoning and hard cost/intervention stops.
7. Four protocols, Gym scoring/compare, human annotation and provenance-separated structured export.
8. React Studio graph/inspection consuming backend, recorded demo, failure/regression coverage, clean install and release artifacts.

<b>Key automated acceptance tests:</b> events survive reload; duplicate writes are idempotent; branch restore checks hashes; rejected criticism cannot mutate approved patch; quarantined/revoked memories never enter approved retrieval; overspent runs cannot request inference; valid/invalid critic fixtures are distinguished by tests; all modes emit the same event format; CLI/Studio/JSON export agree.

## 11. Experiment honesty and judge-facing language

<b>Defensible claim:</b> "DOXA makes agents' epistemic revisions and interventions inspectable, branchable, and evaluable. The initial release demonstrates an integrated research and debugging mechanism."

<b>Hypothesis, not established finding:</b> evidence-gated criticism, controlled memory, branching and bounded reflection could improve recovery and resistance to misleading feedback on certain tasks at acceptable added cost.

<b>Claims to avoid:</b> "DOXA reliably improves reasoning," "DOXA makes models truthful," "different role prompts make independent critics," and "a stochastic fork proves a causal effect."

## 12. Codex/teammate handoff

<b>Build DOXA v0.1.0 as a local-first, auditable epistemic experiment harness.</b> Share one append-only experiment ledger, one deterministic controller and one typed evidence model across Epistemic Git, Counterfactual Engine, False Critic, Memory Tribunal, Self-Correction Gym and Adaptive Reflection. Support Solo Direct, Solo Deliberative, Collaborative Multi-agent and Adversarial Multi-agent; Python/FastAPI/Pydantic/SQLite/Typer backend and [localhost](http://localhost) React/TypeScript/Vite/React Flow Studio. Use a restricted execution sandbox, provider adapters, a \$75 total spending ceiling and a reproducible cache-invalidation fixture with both true and false objections. Require branch lineage, validated restoration, memory retrieval gating, trigger/skip reflection evidence, human annotation, honest costs and reproducible baselines. Prioritize correctness and shared-system integration over superficial interface polish; never misrepresent mock inference, recorded replay, judgment provenance or empirical certainty.
