## Architectural principle

DOXA is one runtime with multiple interfaces and pluggable environments/models. The six research systems operate over common identifiers and an append-only experimental history.

## Layers

### 1. Presentation

<b>CLI</b> for scripting, batch execution, debugging, inspection, export, and headless research workflows.

<b>DOXA Studio</b> for experiment configuration, Agent Council activity, claim/evidence inspection, branch visualization, trajectory comparison, annotation, and evaluation reports.

### 2. Orchestration runtime

Schedules agents and tools, applies operating-mode rules, routes model requests, invokes the Adaptive Reflection controller, enforces budgets, and writes events.

### 3. Core research systems

Epistemic Git, Counterfactual Engine, False Critic, Memory Tribunal, Self-Correction Gym, and Adaptive Reflection. Each consumes and emits structured records through defined contracts rather than hidden shared state.

### 4. Environment adapters

Task-specific implementations of initialize, observe, act, snapshot, restore, verify, and terminate. The code-repair environment is the flagship initial adapter.

### 5. Model/provider adapters

A consistent request/response interface over hosted model APIs, remote self-hosted inference, and possibly local inference. Each adapter declares capabilities such as structured output, native tool calling, streaming, usage reporting, and context constraints.

### 6. Persistence

SQLite or an equivalent lightweight local database for experiment metadata, events, claims, memories, evaluations, and annotations; filesystem or content-addressed artifacts for snapshots, code workspaces, logs, and exports.

## Shared invariants

- Every consequential object has a stable identifier.
- Every branch has ancestry.
- Restoring working state never erases the audit history.
- Model outputs are recorded separately from independent verifier results.
- Human labels, deterministic results, and LLM judgments are typed differently.
- A stored reflection is not automatically trusted memory.
- An accepted criticism is not automatically a correct criticism.
- Re-executing an LLM from the same checkpoint is a new stochastic run unless exact deterministic replay is explicitly supported.

## Process boundary

The frontend should never directly hold provider secrets. Model and environment operations route through the local backend/runtime. Sandboxed task execution must not inherit DOXA's provider credentials.

## Repository concept

The implementation should separate core runtime, research systems, environments, evaluation, annotation, storage, API, CLI, Studio, tests, examples, and documentation so a new model or task adapter does not require rewriting the entire application.

## Locked integration decisions — October 12, 2026

- <b>Primary engineering deliverable:</b> the shared, append-only Experiment Ledger. Every capability reads/writes shared experiment IDs, trajectory IDs, claim/evidence IDs, event IDs, checkpoint IDs, and typed provenance; no private subsystem can become the source of truth for cross-system records.
- <b>Six capabilities remain mandatory:</b> claim versioning, recoverable branching, criticism validation, governed memory, evaluation/annotation, and policy-driven reflection. The six historical project names remain internal references; product-facing names can be consolidated or unobtrusive.
- <b>User-facing product hierarchy:</b> Experiments, Trajectories, and Evidence are primary. Claims, Challenges, Branches, Memory, and Reflection policy appear contextually rather than as six equal branded applications.
- <b>One runtime / two clients:</b> CLI and [localhost](http://localhost) Studio use one command/API layer and one local persistent ledger. No public DOXA website or mandatory cloud backend.
- <b>Invariant extensions:</b> idempotent event writes (stable deduplication keys); separate declaration from verifier result; checkpoint integrity test before branching; budget accounting for every run and branch; stable role/model assignment metadata.
- <b>Security boundary:</b> use loopback-only local API by default, local storage, no third-party telemetry by default; external API inference is opt-in per provider and sends selected task context off-machine. Generated code runs in restricted disposable containers, without host secrets or network by default.
- <b>Operating modes:</b> Solo Direct and Solo Deliberative, Collaborative, Adversarial; multiple roles may use the same underlying model. Shared memory promotion must be explicit.
- <b>Acceptance gate:</b> end-to-end demonstration must show six capabilities interacting on the same persisted trajectory with reloaded CLI and Studio views.
