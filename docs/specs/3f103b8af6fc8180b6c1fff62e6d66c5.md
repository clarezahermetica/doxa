## Purpose

The Counterfactual Engine allows DOXA to revisit consequential decisions when the environment has already changed. It separates changing one's answer from recovering the state in which a different action can actually be attempted.

## Core operations

<b>Checkpoint</b> captures a recoverable environment state and relevant runtime metadata before or after a consequential event.

<b>Restore</b> reconstructs a supported prior state.

<b>Branch</b> creates a new trajectory with ancestry pointing to the restored checkpoint.

<b>Historical replay</b> reconstructs what previously happened from stored events/artifacts.

<b>Counterfactual re-execution</b> runs the model again from restored state, possibly with changed feedback, memory, or policy. It is a new run and may be nondeterministic.

## Knowledge retention

Rollback must not blindly delete everything learned after the checkpoint, but it must also not import obsolete state claims. Candidate retained information should pass through provenance and Memory Tribunal rules. Example: "test X fails under input Y" may remain useful; "file Z currently contains patch P" may become false after restoration.

## Environment requirements

An environment adapter declares whether and how state can be snapshotted. Code-repair may use Git/worktree snapshots plus explicit runtime state. A planning simulator may serialize JSON. A research-writing environment may snapshot a draft and claim store.

## Acceptance tests

1. Snapshot a known environment.
2. Mutate it with a real task action.
3. Restore and verify equality against the recorded checkpoint according to the environment's canonical comparison.
4. Create an alternative branch and persist both outcomes.
5. Retain a validated observation while excluding a state claim made invalid by rollback.
6. Distinguish historical replay from a fresh model re-execution in the UI and export.

## Non-goal

The first release does not claim universal reversal of real-world actions. External side effects require explicit compensating semantics and remain a later extension unless a specific integration safely supports them.

## Integrated ledger acceptance addendum — October 12, 2026

- Expose “Branches” as a contextual trajectory feature; Counterfactual Engine remains an internal technical capability, not necessarily a top-level application.
- Snapshot manifests, restore requests, verified restore integrity checks, fork ancestry and replay-vs-re-execution labels are durable ledger events with stable IDs.
- No restoration success is asserted unless the environment's documented equality/hash predicate passes. Never claim external-world side effects can be undone.
- Acceptance: mutate → verified restore → fork → reload both trajectories from local persistence, with budgets/verification linked to each branch.
